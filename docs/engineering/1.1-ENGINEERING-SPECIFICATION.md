# BetterCP/M 1.1 engineering specification

## Topic HELP system — on hold

HELP development is on hold pending completion of the system-wide TCAP
facility. The [HELP design checkpoint](HELP-1.1-Specification.md) records the
agreed behavior, prototype evidence, open decisions and conditions for resuming.

## Unloaded transient program area

A conventional flat-64K platform shall provide **at least 56 KiB (57,344 record-aligned bytes) of unloaded TPA** unless a measured, documented platform constraint justifies less. Where the platform can safely provide more, its default build should expose that additional memory to applications.

Measure unloaded TPA from the CP/M transient entry at `0100h`, with no optional resident extensions loaded, in complete 128-byte CP/M records. Report the capacity available under the shipped startup configuration separately. To qualify a default layout, run a `.COM` file at its measured maximum size, verify its return to the command prompt, and verify safe rejection of a file one record larger.

| Platform | 1.1 requirement and evidence |
| --- | --- |
| cpmsim RAM | Use the full-RAM layout for the default build. The default distribution provides 57,344 bytes unloaded and 53,760 bytes with ANSISCRN and ADM3A loaded. Each installed provider now uses one additional 256-byte cache page. [1.1 qualification](CPMSIM-1.1-DEFAULT.md) |
| TRS-80 Model 4 | The initial exception is 54,272 bytes unloaded. The current BIOS reserves `F400h–FFFFh` for the keyboard/video mapping. A later 1.x investigation will measure how much RAM temporary mapping can safely recover. [Model 4 assessment](Part13-Final-Assessment-and-Roadmap.md) |
| TRS-80 Model II and future conventional flat-64K ports | Apply the minimum during bring-up and report the measured capacity at qualification. Document any exception with its capacity, affected address range, platform constraint, and prospects for recovery. |

BetterCP/M 1.0 retains its historical 53 KiB unloaded baseline.

## TRS-80 Model II screen backend

The platform capability word for a Model II `SCRN` provider is **0004h**.
The checked Model II loader requires the exact word and a private carrier with
the resident build identity. M2SCRN implements SCRN 1.1 for the shared ADM3A,
VT52 and ANSI personalities. The carrier allocates 1,536 bytes. Loading it
as the first optional module costs 2,816 bytes of TPA in this build, including
the manager overhead.

See the [screen ABI](Unloadable%20Screen%20Backend%20ABI.md) for the complete
platform assignment and the [Model II port](../platform/MODEL2-PORT.md) for
build and qualification status.

## Numeric command search PATH

Unqualified transient commands use an ordered list of up to six canonical
locations. A dot resolves to the caller DU at invocation. The default is
`. A0:`. The list is fixed protected command-environment state with no loss
of unloaded TPA. Use `A0:PATH /DEFAULT` for direct recovery.
[Numeric PATH contract, operator commands and qualification](Numeric-PATH-1.1.md)

## Portable terminal capabilities (TCAP)

**Roadmap decision, 7 November 2026.** Start the shared terminal-capability
design during 1.1, before TYPE, TED and HELP settle their next display
interfaces. The first deliverable is a proposed application contract covering
screen dimensions (including unknown dimensions), optional text emphasis,
required cursor operations and restoration of console state. Identify which
requirements the current monitor, SCRN 1.1 and optional SCX already satisfy.
Account for both unloaded TPA and the cost of any loaded provider.

HELP development resumes after completion of the shared TCAP facility. Review
the contract and its measured costs before selecting an implementation and
assigning it to a release. The broader terminal-personality library remains
separately scheduled. [Design-thread handoff](TCAP-Design-Thread-Handoff.md)
and [terminal design agenda](POST-1.0-TERMINAL-ARCHITECTURE-OUTLINE.md#early-11-design-work)

The [consolidated TCAP engineering proposal](TCAP-Engineering-Proposal.md#consolidated-design-package)
is ready for engineering review as documentation. It covers the consumer
contract, ownership, routing and recovery direction, qualification plan and
remaining measured feasibility gates. It does not approve an ABI, begin
implementation or resume HELP.

The [complete proposed integration design](TCAP-Integration-Design.md) supplies
interface semantics, source responsibilities and the later qualification campaign.
The remaining gates require measured feasibility and runtime evidence; TCAP
is not delivered and no implementation or release assignment is approved.
