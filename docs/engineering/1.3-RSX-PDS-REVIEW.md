# 1.3 review boundary: fixed RSX manager versus configurable PDS

Status: resolved; maintainer selected private helper rebasing. The approved PDS
header and MCL semantics need no change. Memory recovery is PR #683.

## Demonstrated source constraint

The approved proposal correctly requires RSX packing to use the actual PDS low
boundary. Current source has an additional invariant: executable manager helpers
are linked at LY_RSX, exactly 1024 bytes below the old fixed history base.
The extension dispatcher also puts its manager stack at LY_RSX+03FDh.

Relevant sites:

- `extens.mac:EX_RLOAD`: stack at LY_RSX+03FDh, Model 4 entry at LY_RSX;
  checked entry is in CFG but still uses this fixed manager stack.
- `r3entry.mac:RI_COPY/RI_RETURN`: copies 1012-byte helper images to LY_RSX
  and jumps there. Checked entry also snapshots/restores that fixed range.
- `r3cache.mac:FINISH`: restores the manager at LY_RSX.
- `r3final.mac`, `r3prof.mac`, `r3drop.mac`: fixed manager boundary constants.
- Eight transaction helpers and the resolver link at LY_RSX. Their internal
  absolute operands require rebasing if that origin moves.

Canonical addresses (add 0C00h for the two full-RAM profiles):

| Object | Start | End exclusive |
| --- | --- | --- |
| Default PDS | D504h | D5D0h |
| Fixed helper image | D104h | D4F8h |
| Fixed manager stack ceiling | — | D501h |
| PDS with HISTORY Normal and MCL | D484h | D5D0h |
| Largest proposed PDS: H384 + M128 + V512 + metadata12 | D1C4h | D5D0h |

Thus even one optional 128-byte owner overlaps the old manager image and its
stack. Merely changing the final published TPA boundary is insufficient.
Directory checks and owner tests cannot detect this by themselves. The same
problem occurs with Large history. Off/Small/Normal history without optional
owners does not overlap the existing manager.

## Recommended resolution

Make the private helper execution window follow the cold-composed PDS:
manager base = PDS low - 1024. Keep it fixed for the boot session. Derive the
manager stack and packing ceiling from that base. Rebase private helper images
only when loading them, after validating their stored identity/checksum and
relocation metadata. Extend the private helper pack and scratch loader as
necessary, retaining its staged/fallible-read-before-commit transaction model.

This preserves default active-RSX memory cost and charges optional owners for
their actual allocations. It is not a PDS allocator, live resizing, general
third-party allocation, or a move of NDR state. The required new contract is
private overlay relocation/placement, which the initial PDS review did not
specify. Existing public BRSX module behavior and page-zero exits must remain.

This is substantial enough to review explicitly: current checked helper sizes
include R3PROF 998, R3FINAL 982, R3COMIT 1007 and entry 994 bytes, against tight
1000/1012-byte slots. R3CACHE is 1511 of 1536 bytes. New rebasing logic cannot
simply be appended everywhere. The pack and scratch placement need coordinated
changes and focused failed-transaction/NDR/PATH tests.

## Alternatives and their cost

1. **Recommended: rebase the private helpers.** No additional permanent resident
   code or default TPA loss; new private pack/scratch-loader work must be reviewed.
2. **Fixed window below the largest PDS.** Base CDC4h would avoid all proposed
   owner sizes, but sacrifices up to 832 extra bytes with an active RSX under the
   default configuration. It preserves the unloaded floor while imposing an
   unnecessary active-RSX penalty. This is not recommended without explicit
   acceptance of that tradeoff.
3. **Defer expanded compositions.** Stage only Off/Small/Normal HISTORY, keep
   MCL/VAR off and unavailable until the helper work is reviewed. This can make
   a smaller foundation stage useful, but does not complete locked 1.3 scope.

The approved implementation and focused evidence are recorded in
[the RSX window prerequisite](1.3-RSX-WINDOW.md). The sizes above describe the
finding, not the final emitted helpers. Expanded-layout transaction and NDR
checks belong to the following foundation stage.
