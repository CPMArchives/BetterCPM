# BetterCP/M 1.1 — frozen feature scope and release acceptance

**Maintainer clarification, 8 November 2026:** TYPE, TED and HELP were illustrative
consumers, not an exhaustive set of utilities needing TCAP assessment or changes.
The [full utility impact audit](../engineering/TCAP-Utility-Impact-Audit.md) covers all 52 registered utilities and
records a confirmed TED integration regression. Earlier three-name lists must
not be used to infer migration policy. Broader consumer-adoption release scope
is under clarification; compatibility checks apply to every affected utility.
Publication remains held.

**Feature scope frozen: 8 November 2026.** This document records the maintainer's decision that BetterCP/M 1.1 is feature-locked. It does **not** certify a release candidate, qualify new package bytes, or authorize publication. Preparation begins from merged main commit `75e846b128299ff0777cebf5fba4512d1c44f42f` (PR #664); the final release-source commit and artifact hashes must be pinned after release-only changes are accepted.

## Included commitments

1. **Three maintained targets:** patched z80pack cpmsim, TRS-80 Model 4 under trs80gp, and 64 KiB TRS-80 Model II under trs80gp 2.5.8 with the qualified BCM2SS single-sided floppy image format. Keep one shared CCP/BDOS/core implementation. Model II qualification is emulator-specific, not a claim about Models 12/16/16B or physical hardware. See [platform acceptance](../platform/SUPPORT-1.1.md).
2. **Unloaded TPA policy:** at least 57,344 record-aligned bytes (56 KiB) for supported flat 64 KiB configurations, exposing more where safe. The explicitly measured TRS-80 Model 4 exception is 54,272 bytes; do not represent that target as a 56 KiB system. cpmsim defaults to its qualified full-RAM image. See the [1.1 engineering specification](../engineering/1.1-ENGINEERING-SPECIFICATION.md).
3. **Bounded numeric command PATH:** ordered drive/user list with at most six entries, default `. A0:`, dynamic current DU, explicit drive/user resolution, recovery through `A0:PATH /DEFAULT`, and the existing preserved command-tail, loader and error contracts. Ship profile-matched `PATH.COM`; support `/H`, `/HELP`, `/VER` and the established BetterCP/M utility UI standard. See [PATH implementation and qualification](../engineering/Numeric-PATH-1.1.md) and PR #663.
4. **TCAP 2.0:** ship the compact direct-operation TCAP 2.0 facility qualified in PR #664, including the combined unloadable ADM3A, VT52 and ANSI personality/renderer modules for cpmsim, Model 4 and Model II. This is the selected implementation of the previously approved 1.1 terminal-capability work, not a new feature added after freeze. The original TCAP 1.0 and its template/transaction experiments were abandoned, never released, and were superseded during engineering; TCAP 2.0 is an independently versioned interface, not a BetterCP/M release number. Distribute the profile-matched 2.0 modules, public interface/usage guidance and documented legacy paths; qualify their real packaged install/load/unload and client admission on all three platforms. See [TCAP 2.0 ABI](../engineering/TCAP-Direct-ABI.md) and [cross-platform engineering evidence](../engineering/TCAP-Direct-Integration-Results.md).
5. **Established compatibility:** continue the CP/M 2.2 BDOS/BIOS and transient-entry contracts, original-case command-tail behavior where documented, command/CPX/RSX precedence, installation and recoverable-media safeguards. Any known behavioral difference must remain documented. Do not mix 1.1 resident modules or private layout-dependent utilities with earlier System builds.

## Explicit exclusions and maintained research

- **HELP.COM and `HELP.LBR` are not included.** The [HELP design checkpoint](../engineering/HELP-1.1-Specification.md) remains on hold; its production reader, corpus and navigation are unqualified.
- **Abandoned TCAP 1.0 is not included.** The historical 1.0 public/template/transaction candidates are not runtime contracts and need no compatibility shim. The merged TCAP 2.0 direct interface replaces them. The shipped 2.0 implementation is bounded to the qualified fixed 80×24 seven-bit terminal protocols; arbitrary host geometry, the historical eight-bit raw BIOS bypass, universal SCX feature parity, additional personalities and TYPE/TED/HELP migrations are not part of 1.1. Existing SCRN/SCX paths remain available separately as documented.
- Named-directory (NDR) lookup, named PATH entries, multiple-command lines, new scripting, PDS generalization, Model 4 memory-mapping recovery, Model 4 sector-cache optimization, and new port targets are outside this feature freeze.
- New format definitions or a BIOS checksum-capacity increase are not included solely because earlier documentation said to *consider* them for 1.1. Existing qualified 1.0.1 supplemental format behavior may be carried forward without inventing a new commitment.

## Release-only corrections

Changes are allowed only where needed to package, version, document, reproduce or qualify the locked features, or to fix a demonstrated regression that blocks their safe use. Each production correction must identify the failure, affected platforms and resource/compatibility effect, and rerun the applicable acceptance gates. A successful engineering build alone is not a reason to broaden the release. Do not alter or overwrite v1.0 or v1.0.1 packages.

The open [VER query conformance issue #612](https://github.com/CPMArchives/BetterCPM/issues/612) predates 1.1. Reproduce the resident/transient cases against candidate media and record either a narrowly scoped regression correction with new evidence or a specific accepted limitation in the release notes. Do not silently consider an old issue closed. The Model 4 latency issue #559 remains a later performance investigation, not a release-blocking defect absent new evidence. The merged Model II port can be reconciled against issue #523 without expanding the supported machines.

## Required acceptance before `v1.1` publication

1. **Freeze exact inputs:** identify a clean source commit; pin assembler, emulator versions, patched cpmsim source/build and tool dependencies. Record component/utility revisions and matching package identities.
2. **Build immutable target pairs:** fresh System and primary/companion Utilities media for all three targets from one source cut. Verify each private carrier, platform-specific dependency, selected boot file, installed SYSTEM.SYS and utility inventory; reject cross-profile and stale pairs.
3. **Execute final guest tests on those bytes:** each target cold/warm boots and returns from a maximum-size COM and safely rejects one extra 128-byte record; PATH precedence, recovery, `/H`, `/HELP`, `/VER`, qualified loader failures, command tails and SUBMIT/XSUB pass on packaged media. Re-run relevant BDOS/BIOS, disk protection/recovery, optional-module/RSX and installation checks, including native Model II media qualification. For all three targets, explicitly qualify the packaged TCAP 2.0 ADM3A/VT52/ANSI modules: exact same-owner discovery and refusal, legacy/portable rendering and fallback, warm/reconstruction behavior, optional RSX interaction, install-and-boot, complete unload and exact unloaded maximum-COM recovery. Document exceptions and emulator-only coverage. Earlier engineering-candidate receipts cannot stand in for differently hashed release images.
4. **Verify installation and reproduction:** SYSGEN installation, independent cold boot and DUP checks as supported; cpmsim offline runtime reconstruction; source reconstruction and comparable binary outputs; checksummed image, contents and archive readback.
5. **Produce release assets and documentation:** three System packages, three Utilities packages (including Model II primary and companion media), the profile-matched TCAP 2.0 direct-operation modules and client interface material, matching Source and Documentation packages, release notes, notices/license/provenance, checksums, release index and exact qualified evidence. Keep supported platform/format/TCAP boundaries prominent.
6. **Acceptance and publication:** review a machine-readable PASS ledger tied to a single release commit and exact artifact hashes, with no unexplained failures or unqualified substitutions. Only then create the `v1.1` tag on that source revision, attach verified packages and publish GitHub release notes. Do not tag or announce a release as qualified before this gate.
