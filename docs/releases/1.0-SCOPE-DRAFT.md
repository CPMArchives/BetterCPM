# BetterCP/M 1.0 scope — proposal

Status: core-first milestone order approved; overall 1.0 feature inventory remains proposed. Updated 2026-09-07.

The release should be a usable, portable CP/M 2.2 replacement whose existing
features have a defined compatibility boundary and repeatable acceptance tests.
A large backlog is not the release contract.

## Proposed release requirements

- Standard CP/M 2.2 BDOS services and the 17-entry BIOS interface, with supported,
  intentionally unassigned, and reserved operations explicitly documented.
- Reliable file and disk operations: sequential/random I/O, extents, allocation,
  directory operations, drive/user switching, protection and error recovery.
- Portable common code and separate platform adapters. The agreed 1.0 targets
  are TRS-80 Model 4 under trs80gp, z80pack/cpmsim, and RomWBW. Qualify each
  explicitly; RomWBW is newly selected and is not yet implemented or validated.
- Preserve at least 53 KiB TPA in the present ordinary RAM build without optional
  RSXs. Report the ROM build's address-space and RAM costs separately.
- Cold/warm boot, transient return, and reconstructible command environment that
  remain correct after a transient overwrites its entire advertised TPA.
- ROM-able system. The user has made this a release requirement. Confirm whether
  the required profile is execution in ROM or ROM-to-RAM bootstrap; provisionally
  plan for immutable executable code and constants, separate writable RAM state,
  and explicit initialization from default templates.
- Stable, documented interfaces for the existing CPX/RSX facilities, including
  unload and warm-boot recovery. No promise of a future device-driver framework.
- Working configuration and disk utilities: current CONFIG F/G/I, H saving the
  current boot disk's settings, DUP A/B/C, and SYSGEN installation from A: to a
  compatible prepared target. Qualify supported formats against
  the capabilities of each platform adapter; distinguish mapper support from
  actual hardware/media testing.
- A reproducible, redistributable distribution with the basic command environment
  and an explicitly chosen set of essential transient utilities.

## Date/time support — confirmed 1.0 requirement

Provide one documented date/time service with interchangeable clock-provider
RSXs. Hardware-specific register access and emulator clock calls belong to the
provider, so installing the appropriate RSX supplies the user's clock without
rebuilding BIOS/BDOS or teaching applications about that device. A provider
library can grow as additional hardware is supported; the initial tested provider
inventory must be explicit, not a claim to support every clock at release.

The agreed legacy compatibility baseline comprises DateStamper, ZSDOS/ZDDOS,
P2DOS, CP/M Plus, and DOS+/Z80DOS. Prioritize DateStamper and ZSDOS/ZDDOS in
implementation and testing, reflecting the user's expected installed-software
coverage; this is a priority decision, not a measured historical popularity claim.
The requirement is that existing date/time utilities run unmodified. Qualify
identity/discovery probes, call numbers and entry points, buffer/register/error
contracts, and applicable file-stamp operations and disk layouts. Provider clock
reads alone do not establish compatibility. Maintain a per-family and per-utility
acceptance matrix; unresolved variants remain explicit gaps. Resolve conflicts
with BetterCP/M's private calls before freezing the core interface.

Define the common contract during core qualification: date/time representation,
range and resolution; local-time/UTC policy; query/read and optional set operations;
capability and validity reporting; and absent/unset/failing-clock results. Setting
a clock is supported only when the provider explicitly offers that capability.
One active provider should serve the common interface; provider replacement and
unload must leave no dangling hooks or callable pointers. No installed provider
means an explicit unavailable result, not invented time. Clock drivers consume
RSX memory only while loaded; account separately for any fixed dispatch cost.

TIME.COM and other consumers use the common service. Provider implementation,
installation and application-facing tools belong to later milestones, while the
core-facing interface is settled before freezing the core. Test date rollover,
calendar validation, unavailable/read-only providers and load/unload/WBOOT behavior.

Clock service and on-disk timestamps are separate implementation layers. Legacy
stamp operations and layouts needed by the agreed utility compatibility targets
must be included in the acceptance matrix; the exact native layout and handling
of incompatible legacy expectations still require design. Whether any clock configuration
belongs in persistent DATA also remains an inventory decision.

## RomWBW target — confirmed

Implement a BetterCP/M platform adapter using RomWBW's HBIOS interface for
hardware services, plus a clock-provider RSX for its clock service. Keep the
common BIOS/BDOS independent of RomWBW-specific calls and memory arrangements.

Before implementation, select and pin a RomWBW version and a concrete supported
hardware/emulator configuration for repeatable qualification. Audit the HBIOS
calling conventions, memory reservations/banking, disk geometry and drive mapping,
boot handoff and clock capabilities. Qualify cold/warm boot, console and disk I/O,
TPA boundaries, core conformance and clock-provider lifecycle on that configuration.
Do not claim testing of every RomWBW machine from one configuration's results.

Booting BetterCP/M under RomWBW and executing BetterCP/M code from ROM are
separate acceptance criteria; the target port does not automatically prove the
core's ROM-ability. Existing tests on trs80gp and z80pack remain part of release
qualification.

## Decisions still needed before scope approval

- ROM execution profile and a concrete emulator configuration that enforces
  read-only code. Loading a RAM image from ROM is not execution in place.
- Essential utility inventory: choose replacements or suitably licensed existing
  utilities. Do not silently require new implementations of every stock tool.
- Which remaining CONFIG settings belong in 1.0. A-E still contain placeholders;
  reproducing every Montezuma hardware menu is not yet a settled requirement.
- Whether installing a system onto a different disk is a 1.0 requirement. Current
  H work is deliberately limited to saving the existing boot disk's configuration.

## Current evidence and release gaps

The unified BDOS has the standard 0-40 dispatch, with reserved entries 38/39
returning the documented unsupported result. The current built BDOS image is
3,390 bytes, including local state/stack. The baseline RAM build advertises
54,273 bytes of TPA. These are implementation/memory facts, not a conformance
certificate.

The BIOS has the standard vector table and separate platform code. Optional
LIST/PUNCH/READER services remain unassigned. The z80pack adapter currently
reports fixed geometry and rejects physical configuration, geometry changes and
WD-style track formatting; its acceptance matrix must reflect that limitation.

The latest DUP work passed a complete 800K format/verify and focused copy/check
and error tests. The backlog still calls for a complete compatibility-suite rerun
after the resident rewrites. Use the user's existing [CP/M 2.2 Compatibility Suite](https://github.com/CPMArchives/cpm-2.2-compatibility-suite)
as the conformance authority, rather than creating a replacement suite. Retrieved
revision: `1443bc1` (2026-09-07), local checkout `../cpm-compatibility`.
Its current inventory is twelve test executables across eleven logical tools:
ENTRYTST, BDOSTEST, FILETEST, RANDTEST, DIRTEST, CONSTEST, CCPTEST, DISKTEST,
BIOSTEST, ERRTEST, ECOTEST and CPUTEST, plus SCRATCH for fixture preparation.
BetterCP/M's older test-disk builder includes only seven of these executables;
update that integration before claiming a complete run. Record the exact suite
and system revisions, retain case-level evidence, and follow the suite's distinction
between requirements, observations, claimed profiles and untested manual procedures.
Run the applicable cases against the release candidate, rather than extrapolating
from targeted passes. ROM write-protection checks are additional BetterCP/M
architecture tests; they do not replace this CP/M compatibility suite.

Current ROM blockers include writable BDOS variables and stack in its assembled
image, writable BIOS state and configuration records, and the RAM/disk-based
control/reload paths. An address/write audit is required before claiming there is
no self-modifying code. A ROM profile needs its own map, initializer and test;
merely changing the assembler origin is insufficient.

CONFIG H is in implementation/testing. Do not mark it complete until saved
physical/logical settings survive a cold boot, unrelated disk contents remain
unchanged, and failed writes/verification and recovery have been exercised.

## Milestone 1: qualify and finalize the system core

The user has established engineering and compatibility qualification of the core
as the first goal. BIOS, BDOS and their accompanying structures are finalized
when this milestone passes. CCP and other 1.0 milestones build on that baseline.

Core scope includes the public call interfaces, page-zero contracts, disk and
configuration structures (DPHs, DPBs, allocation/checksum vectors and bindings),
buffers, stacks, memory ownership, hardware-adapter boundaries, initialization,
and core responsibilities during cold boot, warm boot and transient return.
Existing command and utility programs serve as test drivers where needed; their
complete feature sets are not prerequisites for declaring the core qualified.
Core interfaces used by extensions belong in this boundary; higher-level command
and extension-product features retain their own later acceptance milestones.

The core must include a dedicated reserved persistent DATA region, as clarified
by the user. Its placement is fixed above the downward-growing RSX region;
RSX allocation and reconstruction of the lower command environment must not move
DATA. The canonical DU/named-directory map is required there; the other contents
remain undecided. Define the published base/layout, lifetimes, reset semantics
and measured memory cost as part of core qualification. The current scattered implementation
is not by itself completion of this requirement.

Exit criteria:

1. Complete the engineering audit, including the agreed ROM profile, writable
   state separation, memory bounds, TPA protection and error recovery.
2. Account for all 627 compatibility propositions by ownership. Run and resolve
   the applicable core requirements and claimed profiles on all three agreed targets;
   retain observations and explicitly justified exclusions. A required manual
   test is unfinished until performed. CCP/utility-owned cases are assigned to
   later milestones, not counted as core passes or dropped from the release plan.
3. Exercise core integration paths across multiple calls, disk/media failures,
   configuration changes and repeated warm boots. Attribute failures to their
   responsible component rather than treating every test-driver failure as BDOS.
4. Freeze the qualified core interfaces and structure layouts, publish their
   contracts and memory accounting, and retain reproducible binaries, exact
   source/suite revisions and case-level results for the baseline.

Finalized means an engineering and compatibility baseline, not immunity from
future defect fixes. Any subsequent core change requires the relevant regression
checks; an interface change requires an explicit baseline/version decision.

## Later 1.0 milestones

The stock CCP ships with only GET, JUMP, PEEK/P, POKE, GO and SAVE as built-in
commands. RCP.CPX supplies DIR, ERA, TYPE, REN, USER, CLS, VER, COPY and MOVE.
This is the agreed command boundary;
transitional standard-command implementations in the core CCP must be removed
after their CPX replacements are qualified. Detailed semantics of the six core
commands require specification; names alone do not establish their contracts.

SAVE was added to the stock resident inventory on 2026-09-08: saving an
existing memory image must not require loading a transient over that image.
Its existing RCP.CPX implementation must migrate to the core CCP.

Full CP/M 2.2 SUBMIT/XSUB behavioral compatibility is required for 1.0, including
existing command-file and submitted-program-input workflows. Further extensions,
such as flow control, are loadable CPX facilities rather than core CCP commands.
The selected extended feature inventory remains separate from required stock
compatibility. Any input support that must remain active during a transient must
use protected runtime state/code; it cannot depend on reclaimable CPX storage.


- Finalize the CCP and its command environment against the qualified core,
  including CCP-owned compatibility cases and agreed command-input behavior.
- Qualify utilities, batch facilities and remaining configuration/installation
  workflows against their own agreed scope and acceptance criteria.
- Assemble and qualify the complete distribution, including installation,
  recovery, documentation and end-to-end application workflows.

CONFIG H remains work in progress with changes preserved; completing its entire
utility qualification is not the first core milestone. Its tests may supply
useful evidence for core configuration and disk-write behavior.

Post-1.0 considerations already discussed include a disk editor, device-specific
loadable BIOS extensions, format catalogue replacement/conversion, and expansion
of optional disk services. They should not silently enlarge the 1.0 contract.
