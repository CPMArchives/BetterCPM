# BetterCP/M 1.0 scope — proposal

Status: reduced 1.0 boundary approved; final utility inventory remains open. Updated 2026-09-21.

The release should be a usable, portable CP/M 2.2 replacement whose existing
features have a defined compatibility boundary and repeatable acceptance tests.
A large backlog is not the release contract.

## Proposed release requirements

- Standard CP/M 2.2 BDOS services and the 17-entry BIOS interface, with supported,
  intentionally unassigned, and reserved operations explicitly documented.
- Reliable file and disk operations: sequential/random I/O, extents, allocation,
  directory operations, drive/user switching, protection and error recovery.
- Portable common code and separate platform adapters. The agreed 1.0 targets
  are TRS-80 Model 4 under trs80gp and z80pack/cpmsim. Qualify each explicitly.
  RomWBW support is staged after 1.0 and is not a 1.0 release gate.
- Preserve at least 53 KiB usable TPA in the default ordinary RAM build without
  optional RSXs. Treat this as a continuous build and qualification gate across
  all remaining 1.0 work, rather than a final-release measurement. Report the
  ROM build's address-space and RAM costs separately.
- Cold/warm boot, transient return, and reconstructible command environment that
  remain correct after a transient overwrites its entire advertised TPA.
- ROM-able system. Acceptance requires actual execution in place of immutable
  BetterCP/M code under enforced write protection, with all mutable state in RAM
  and initialized explicitly from immutable defaults. A ROM-to-RAM bootstrap may
  be supported, but does not satisfy this acceptance requirement.
- Stable, documented interfaces for the existing CPX/RSX facilities, including
  unload and warm-boot recovery. No promise of a future device-driver framework.
- Working configuration and disk utilities: current CONFIG F/G/I, H saving the
  current boot disk's settings, DUP A/B/C, and SYSGEN installation from either
  an installed source disk or `SYSTEM.SYS` to a compatible prepared target.
  Qualify supported formats against
  the capabilities of each platform adapter; distinguish mapper support from
  actual hardware/media testing.
- A reproducible, redistributable distribution with the basic command environment
  and an explicitly chosen set of essential transient utilities.

## Clock-provider service — confirmed 1.0 requirement

Provide P2DOS-compatible Function 200 GET and Function 201 SET with
interchangeable clock-provider RSXs. Hardware-specific register access and
emulator clock calls belong to the provider, so installing the appropriate RSX
supplies the user's clock without rebuilding BIOS/BDOS or teaching applications
about that device. A provider library can grow as additional hardware is
supported; the initial tested inventory must be explicit.

This is BetterCP/M's general hardware-independent clock service. It adopts the
P2DOS selectors and five-byte record as a compact established convention;
P2DOS clock-call compatibility is a consequence rather than the design goal.

The required 1.0 provider inventory is FreHD under trs80gp/Model 4 and the RTC
interface under z80pack/cpmsim. Both may be read-only. `TIME.COM` displays the
sample and reports the active provider. Unhandled 200/201 calls mechanically
return 0FFh, defined by the public ABI as UNAVAILABLE.

The common contract uses the P2DOS five-byte record. Before implementation is
frozen, verify exact P2DOS successful-return behavior and assign only the minimal
status values needed for success, unavailable, unsupported SET, and operation
failure. Version 1.0 does not require a writable provider.
One active provider should serve the common interface; provider replacement and
unload must leave no dangling hooks or callable pointers. No installed provider
means an explicit unavailable result, not invented time. Clock drivers consume
RSX memory only while loaded; account separately for any fixed dispatch cost.

TIME.COM and other native consumers use Functions 200/201. TIME.COM includes
the SET request path and reports a read-only provider, although the required
platform providers need not complete SET successfully. Test date rollover,
calendar validation, unavailable/read-only providers and load/unload/WBOOT
behavior. Ship `P2DOS.MAC` as the provider template with a stable `CLKHW.INC`
source contract and library modules for FreHD and z80pack. A porter adds another
conforming `CLK*.INC` module without editing the common provider. Other clock
schemes remain possible through separately specified RSX interfaces, but 1.0
qualifies only Functions 200/201.

Except for the standard Functions 200/201 clock interface, historical API
adapters and on-disk timestamps are separate later-1.x features. The remaining
candidate compatibility families are DateStamper, ZSDOS/ZDDOS, CP/M Plus, and
DOS+/Z80DOS, with DateStamper and ZSDOS/ZDDOS first. No 1.0 claim is made that
their utilities run unmodified or that any historical stamp layout is
supported. Native filesystem timestamp design, file-stamp operations,
`TIME.COM` timestamp editing, and host-tool/cpmtools integration are deferred.

BetterCP/M Function 200 currently conflicts with the historical P2DOS get-time
call. The HELLO and ECHO proof carriers also occupy Functions 201 and 203 only
to exercise RSX chaining; they are tests, not permanent application services.
Before the 1.0 ABI is frozen, migrate the inventoried private services to the
adopted 176-199 namespace, remove both proof services from the released
namespace, rebuild their clients, and adapt the clock-provider RSXs to intercept
200/201 with their inherited P2DOS get/set meanings. Any retained test selectors
must be explicitly experimental. This is clock-call compatibility;
it does not promise P2DOS file timestamps or broader P2DOS emulation in 1.0.

## RomWBW release staging — confirmed

RomWBW is deliberately outside the 1.0 release contract. A bounded basic port is
a candidate for the first suitable post-1.0 minor release, 1.1 or 1.2. It will
use RomWBW's HBIOS interface for console, block-device, boot, and clock services
while keeping BetterCP/M inside its existing 64 KiB execution model. It will pin
one RomWBW/HBIOS version and one repeatable hardware or emulator configuration,
and it will not expose RomWBW memory banks to the BetterCP/M core, PDS, RSXs, or
transient programs. Qualification covers cold/warm boot, console and disk I/O,
TPA boundaries, applicable core conformance, and clock-provider lifecycle on
that configuration; it does not imply support for every RomWBW machine.

Full RomWBW support is a 2.0 architectural target. It may use additional banks
and therefore requires explicit bank ownership and allocation, bank-qualified
references, inter-bank call and copy services, bank-aware PDS/RSX/transient
lifecycles, reconstruction across bank changes, and a generalized firmware and
device architecture. These contracts are not to be added incrementally to the
1.0 ABI.

The 1.0 ROMability requirement remains independent of RomWBW. It covers immutable
code and constants, separate writable RAM state, defined initialization and reset
behavior, and qualification under enforced write protection. A later HBIOS port
does not by itself prove execution of BetterCP/M code from ROM.

The ROM acceptance test must execute BetterCP/M code directly from the protected
ROM region, attempt representative cold-boot, warm-boot, disk/configuration and
extension reconstruction paths, and demonstrate that none writes to that region.
All stacks, variables, live configuration, disk state and reconstruction state
must reside in identified RAM allocations. Copying the executable image to RAM
before entering it is useful boot behavior but is not evidence for this profile.

## Decisions still needed before scope approval

- Select the concrete emulator or hardware configuration used to demonstrate
  the confirmed ROM execution-in-place profile under enforced write protection.
- Essential utility inventory: choose replacements or suitably licensed existing
  utilities. Do not silently require new implementations of every stock tool.
- Which remaining CONFIG settings belong in 1.0. A-E still contain placeholders;
  reproducing every Montezuma hardware menu is not yet a settled requirement.

SYSGEN installation onto a compatible prepared target is already a 1.0
requirement. Cross-format conversion and installation onto media whose target
adapter cannot represent the selected format are outside that promise unless a
required 1.0 platform demonstrates a blocking need.

## Current evidence and release gaps

The unified BDOS has the standard 0-40 dispatch, with reserved entries 38/39
returning the documented unsupported result. The current built BDOS image is
3,390 bytes, including local state/stack. The baseline RAM build advertises
54,273 bytes of TPA. These are implementation/memory facts, not a conformance
certificate.

The BIOS has the standard vector table and separate platform code. Optional
LIST/PUNCH/READER services remain unassigned. The z80pack adapter currently
reports fixed geometry and rejects physical configuration, geometry changes and
WD-style track formatting; its acceptance matrix must reflect that limitation.

The latest DUP work passed a complete 800K format/verify and focused copy/check
and error tests. The backlog still calls for a complete compatibility-suite rerun
after the resident rewrites. Use the user's existing [CP/M 2.2 Compatibility Suite](https://github.com/CPMArchives/cpm-2.2-compatibility-suite)
as the conformance authority, rather than creating a replacement suite. Retrieved
revision: `1443bc1` (2026-09-07), local checkout `../cpm-compatibility`.
Its current inventory is twelve test executables across eleven logical tools:
ENTRYTST, BDOSTEST, FILETEST, RANDTEST, DIRTEST, CONSTEST, CCPTEST, DISKTEST,
BIOSTEST, ERRTEST, ECOTEST and CPUTEST, plus SCRATCH for fixture preparation.
BetterCP/M's older test-disk builder includes only seven of these executables;
update that integration before claiming a complete run. Record the exact suite
and system revisions, retain case-level evidence, and follow the suite's distinction
between requirements, observations, claimed profiles and untested manual procedures.
Run the applicable cases against the release candidate, rather than extrapolating
from targeted passes. ROM write-protection checks are additional BetterCP/M
architecture tests; they do not replace this CP/M compatibility suite.

Current ROM blockers include writable BDOS variables and stack in its assembled
image, writable BIOS state and configuration records, and the RAM/disk-based
control/reload paths. An address/write audit is required before claiming there is
no self-modifying code. A ROM profile needs its own map, initializer and test;
merely changing the assembler origin is insufficient.

CONFIG H is in implementation/testing. Do not mark it complete until saved
physical/logical settings survive a cold boot, unrelated disk contents remain
unchanged, and failed writes/verification and recovery have been exercised.

## Milestone 1: qualify and finalize the system core

The user has established engineering and compatibility qualification of the core
as the first goal. BIOS, BDOS and their accompanying structures are finalized
when this milestone passes. CCP and other 1.0 milestones build on that baseline.

Core scope includes the public call interfaces, page-zero contracts, disk and
configuration structures (DPHs, DPBs, allocation/checksum vectors and bindings),
buffers, stacks, memory ownership, hardware-adapter boundaries, initialization,
and core responsibilities during cold boot, warm boot and transient return.
Existing command and utility programs serve as test drivers where needed; their
complete feature sets are not prerequisites for declaring the core qualified.
Core interfaces used by extensions belong in this boundary; higher-level command
and extension-product features retain their own later acceptance milestones.

The core must include a dedicated Persistent Data Segment (PDS). Its placement
is fixed above the downward-growing RSX region; ordinary RSX allocation and
command reconstruction must not move existing PDS allocations. For 1.0, define
the published base/layout, version, complete fixed owner inventory, lifetimes,
initialization, reset semantics, failure behavior, and measured memory cost.
The existing bounded history state may remain in that inventory.

A general allocator, migration, configurable sizing, and controlled runtime
expansion are later 1.x capabilities. Named directories, PATH, and NDR storage
are also later 1.x features and therefore are not 1.0 PDS owners. See
`docs/architecture/18 Persistent Data Segment.txt` for the broader design
direction; its full feature set is not the 1.0 release contract.

Exit criteria:

1. Complete the engineering audit, including the agreed ROM profile, writable
   state separation, memory bounds, TPA protection and error recovery.
2. Account for all 627 compatibility propositions by ownership. Run and resolve
   the applicable core requirements and claimed profiles on both agreed 1.0 targets;
   retain observations and explicitly justified exclusions. A required manual
   test is unfinished until performed. CCP/utility-owned cases are assigned to
   later milestones, not counted as core passes or dropped from the release plan.
3. Exercise core integration paths across multiple calls, disk/media failures,
   configuration changes and repeated warm boots. Attribute failures to their
   responsible component rather than treating every test-driver failure as BDOS.
4. Freeze the qualified core interfaces and structure layouts, publish their
   contracts and memory accounting, and retain reproducible binaries, exact
   source/suite revisions and case-level results for the baseline.

Finalized means an engineering and compatibility baseline, not immunity from
future defect fixes. Any subsequent core change requires the relevant regression
checks; an interface change requires an explicit baseline/version decision.

## Later 1.0 milestones

The stock CCP ships with only GET, JUMP, PEEK/P, POKE, GO and SAVE as built-in
commands. RCP.CPX supplies DIR, ERA, TYPE, REN, USER, CLS, VER, COPY and MOVE.
This is the agreed command boundary;
transitional standard-command implementations in the core CCP must be removed
after their CPX replacements are qualified. Detailed semantics of the six core
commands require specification; names alone do not establish their contracts.

SAVE was added to the stock resident inventory on 2026-09-08: saving an
existing memory image must not require loading a transient over that image.
Its existing RCP.CPX implementation must migrate to the core CCP.

Full CP/M 2.2 SUBMIT/XSUB behavioral compatibility is required for 1.0, including
existing command-file and submitted-program-input workflows. Further extensions,
such as flow control, are loadable CPX facilities rather than core CCP commands.
The selected extended feature inventory remains separate from required stock
compatibility. Any input support that must remain active during a transient must
use protected runtime state/code; it cannot depend on reclaimable CPX storage.


- Finalize the CCP and its command environment against the qualified core,
  including CCP-owned compatibility cases and agreed command-input behavior.
- Qualify utilities, batch facilities and remaining configuration/installation
  workflows against their own agreed scope and acceptance criteria.
- Assemble and qualify the complete distribution, including installation,
  recovery, documentation and end-to-end application workflows.

CONFIG H remains work in progress with changes preserved; completing its entire
utility qualification is not the first core milestone. Its tests may supply
useful evidence for core configuration and disk-write behavior.

Post-1.0 considerations already discussed include the staged RomWBW work above,
a conventional third-platform evaluation, a disk editor, device-specific
loadable BIOS extensions, format catalogue replacement/conversion, and expansion
of optional disk services. The
[third-platform assessment](../engineering/POST-1.0-THIRD-PLATFORM-ASSESSMENT.md)
prefers Cromemco after 1.0 but assigns no release. These items should not silently
enlarge the 1.0 contract.

## Pre-roadmap freeze

Before returning to Stage 3, the following boundaries are frozen:

1. The two 1.0 qualification targets are trs80gp/Model 4 and z80pack/cpmsim.
   A bounded single-bank RomWBW/HBIOS port is a 1.1 or 1.2 candidate. Cromemco
   and IMSAI remain possible later 1.x validation targets without an assigned
   release. Bank-aware generalized firmware and full RomWBW integration remain
   2.0 work.
2. Historical Cromemco hybrid-density media establish a real future requirement
   for track-range geometry, including tracks whose encoding, sector count or
   sector sizes differ. Record that requirement, but do not design it during
   1.0. FDF/FDB v1 remains frozen unless a required 1.0 format proves it
   insufficient.
3. The 1.0 ROM profile is execution in place under enforced write protection,
   with every mutable object in RAM. ROM-to-RAM loading does not pass that gate.
4. Every default 1.0 build and relevant integration test must preserve at least
   53 KiB usable TPA. A change that falls below the floor is not accepted without
   an explicit scope or architecture decision.

With these boundaries recorded, the critical path is to finish Stage 3, approve
the remaining 1.0 boundary, execute Stages 4 through 7, complete the explicit
Stage 8 architecture reconciliation gate, and then implement the frozen
[1.0 roadmap](1.0-ROADMAP.md). Further machine surveys, 2.0 banking design,
mixed-track FDB design and final utility selection wait for their assigned
decision points.
