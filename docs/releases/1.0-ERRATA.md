# BetterCP/M 1.0 errata

## XSUB companion must be copied to A0

Recorded 4 November 2026. Applies to the locked cpmsim and Model 4 1.0
packages. Correction is targeted for **1.01**; the 1.0 package lock stands.

The primary Utilities Disk supplies both `XSUB.COM` and `BATCHIO.RSX`.
However, the current RSX loader opens companions in drive A, user 0 (A0).
Running `B:XSUB` from A0 does not make it search B for `BATCHIO.RSX`.
If BATCHIO is not already loaded and its companion is absent from A0,
activation cannot load it and reports `Xsub Load Error`.

### Workaround

With the primary Utilities Disk mounted as B, use a writable System Disk
on A and select drive A, user 0. At the `A0>` prompt, enter:

```text
COPY B:BATCHIO.RSX A:BATCHIO.RSX
B:XSUB
```

Keep the matching `R3PACK.RSX` manager runtime on A0 as well. Use companions
from the same release. `XSUB /H` and `/VER` return before loading the provider;
successful query output does not establish that BATCHIO can be loaded.

### Planned 1.01 correction

Resolve the mismatch between the supplied Utilities Disk location and XSUB's
companion-loading requirements, so the supplied setup works without this
undocumented manual staging step. Select the packaging/installation or loader
change after reviewing the existing CPX/RSX loading and reconstruction rules;
this erratum does not authorize a general loader-search redesign.

Acceptance must cover a clean supported installation with XSUB and BATCHIO
on the Utilities Disk, activation from A0, actual submitted Function-10 input,
and warm-boot reconstruction on both platforms. Query-only execution is
insufficient. The limitation is established by source and package-inventory
review; no new runtime qualification or implemented fix is claimed here.

See [XSUB in the User's Guide](../manuals/Command-and-Utilities-Reference.md#xsub) and
the [1.01 work record](../engineering/UI-Conformance-Matrix.md#release-disposition-and-101-scope).

## FDB main-menu presentation

Recorded 4 November 2026. Correction is targeted for **1.01**, with the
1.0 release/package lock retained.

The locked FDB.COM displays a compact menu headed by `Working catalogue:`
and uses the prompt `Choice:`. It does not provide the version heading,
grouped bracketed choices and bracketed choice prompt required by
Engineering Specification 209. This is a known presentation inconsistency;
it is not a claim that the 108-entry DISK.FDB catalogue is defective.

For 1.0, use the displayed letter choices and Q or BREAK to exit. The 1.01
correction must preserve the command mappings and exit behavior while restoring
the specified menu presentation. A local development candidate is preserved,
but its focused checks do not establish Model 4 qualification or release
acceptance. Review and qualify the final changed artifact before shipping it.

## ANSI host terminal size

Recorded 4 November 2026. The 1.0 operating requirement is an ANSI-capable
host terminal of **at least 80 columns by 24 rows**, with a normal full-screen
scrolling region, when using ANSISCRN. The existing
[screen-backend contract](../engineering/Unloadable%20Screen%20Backend%20ABI.md)
already specifies that minimum. No binary correction or replacement freeze
is made by this documentation update.

With ANSISCRN and ANSI loaded, newly drawn CONFIG output was garbled in a
77-by-20 macOS Terminal window. CONFIG worked before loading ANSI. Enlarging
the same window and restarting CONFIG restored the menu without unloading
the modules. Shrinking an already drawn menu did not immediately garble it;
exiting and starting CONFIG again at the smaller size did. Recovery was also
reported at 80 by 22, sufficient for this menu, but not qualification of the
complete backend or other applications at that size.

### Workaround for 1.0

1. Exit the affected utility normally; in CONFIG use BREAK (Ctrl-C).
2. Enlarge the host terminal to at least 80 columns by 24 rows.
3. Start the utility again so it redraws at the supported size.

Set the macOS Terminal profile's Window Size for future sessions as described
in the [installation guide](../platform/CPMSIM-INSTALLATION.md#terminal-display-size).
The distributed launcher does not yet enforce the size. A maintainer-local
launcher customization is not a feature of the frozen packages.

### Planned 1.01 handling

Review smaller-window behavior and a host-side warning or size check. Decide
whether to enforce the documented minimum or support smaller dimensions;
include resize followed by redraw in acceptance checks. Cover the reported
77-by-20 case, the supported 80-by-24 baseline, and larger windows without
regressing the existing console and screen-provider workflows. This records
unfinished work; it does not claim an automatic guard or a verified code fix.

The [evidence summary](../engineering/evidence/2026-11-04-ansi-terminal-size.json)
separates user observations from automated replay. The emulator, original
shipped files and reserved system tracks matched the qualified baseline.
Automated terminal rendering did not reproduce the garbling, even at 77 by 20;
the exact low-level mechanism remains unproven. Publication remains on hold.

### v1.0.1 source correction

A [cpmsim-only launch guard](../engineering/CPMSIM-Terminal-Size-Guard.md)
now refuses interactive output terminals below 80x24 and explains how to
resize and retry. This is a source candidate with focused validation; the
locked 1.0 packages above remain unchanged. It does not enforce live resizing,
change Model 4, or establish a rendering fix for smaller windows.
