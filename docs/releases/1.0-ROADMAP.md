# BetterCP/M 1.0 Roadmap

## 1.0 OS implementation milestone — 2026-10-06

With PR #137 merged, retained OS implementation Items 1–6 are complete.
This marks completion of the planned BetterCP/M 1.0 OS feature implementation,
following the completed architecture program. It is a distinct milestone from
release readiness: Items 7–9 still cover utility selection and completion,
distribution assembly, documentation, and final qualification of frozen release
artifacts. The cpmsim environment reproducibility requirement also remains.
Qualification may reveal defects requiring correction; no additional OS feature
stage is implied by those release gates.

The project remains in development toward 1.0. This milestone does not assign
a new numeric release version or declare a release candidate.

## Remaining 1.0 implementation correction — 2026-10-15

VT52.RSX must be reimplemented as VT52 monitor support, analogous to
ADM3A.RSX providing ADM-3A support. This is required before 1.0; it is
implementation work, not merely final validation. See
[VT52 monitor scope correction](#vt52-monitor-scope-correction--2026-10-15).

## Status and authority

This is the canonical ordering of the remaining BetterCP/M 1.0 work. The
project backlog records individual tasks, architecture documents define
accepted contracts, and engineering specifications record implementation and
qualification evidence. None of those lists may silently reorder this roadmap
or collapse an architecture stage into its later implementation work.

Stages 1 and 2 established the project-wide ABI design conventions and the
resident-service ABI/registry. Stages 3 through 8 are complete, making the
implementation program the current critical path. This revision deliberately narrows the remaining
design stages and moves HISTORY
service redesign, named directories/PATH, a general dynamic PDS allocator, and
broad historical date/time compatibility to later 1.x work. A usable first
release is the goal; the backlog is not the release contract.

## Architectural critical path

### Stage 3 — Complete stateful RSX reconstruction

Stage 3 completed carrier normalization and the transactional reconstruction
coordinator under the then-provisional Function 202 selector. It connected
prospective layout planning, pointer preparation, snapshot construction,
movement and disk-free commit; preserved declared state and internal pointers;
and kept failed transactions from changing the live profile. Stage 6 later
froze Function 177 as the production RSX profile-control and reconstruction
selector. Function 202 is historical implementation state; the coordinated
migration to Function 177 is complete and no 1.0 production alias remains.

The prepared append/removal pipeline reaches commit, persistent-profile
publication, resolver restoration, and
resident self-retirement (engineering specification 151). The legacy manager,
validator, publisher, and version-1 carrier path have been removed. The complete
pipeline has passed cross-platform stateful relocation, rollback, warm-boot and
immutable-code qualification. Stage 3 is complete.

### Final 1.0 boundary — frozen

No Stage 3 implementation finding invalidated this reduced release boundary:

- trs80gp/Model 4 and z80pack/cpmsim are the two 1.0 targets;
- the default configuration retains at least 53 KiB usable TPA;
- the 1.0 ROM profile executes immutable code in place under enforced write
  protection in the selected z80pack/cpmsim qualification environment, with all
  mutable state in RAM;
- terminal-capability redesign is post-1.0;
- a bounded single-bank RomWBW/HBIOS port is a 1.1 or 1.2 candidate; and
- generalized bank-aware firmware and full RomWBW integration are 2.0 work;
- the existing bounded persistent command history is sufficient for 1.0;
  `HISTORY.RSX` redesign is later 1.x work;
- canonical `DU:` operation is sufficient for 1.0; named directories, PATH,
  NDR management, and their command integration are later 1.x work;
- the fixed, versioned 192-byte 1.0 PDS contains only built-in command history;
  general allocation, migration, and controlled runtime expansion are later
  1.x capabilities;
- writable resident objects are classified as bounded PDS state, fixed
  subsystem state, stacks or temporary/shared workspace before placement;
  temporary storage may be statically overlaid only after proving mutually
  exclusive lifetimes;
- mutable objects initialized from constants use immutable ROM templates and
  RAM live instances; E300h remains a planning boundary rather than ABI;
- FDF/FDB, normalized disk state, CONFIG, DUP, SYSGEN, and installation remain
  1.0 requirements;
- 1.0 retains the callable `TIME` ABI as its native clock service, keeps
  `TIME.COM` on that service, and qualifies read-only FreHD and z80pack
  providers; the separate `P2DOS.RSX` frontend supplies Functions 200/201 without
  duplicating hardware code; separate four-byte and five-byte BDOS 104/105
  frontends are bounded optional candidates only after `P2DOS.RSX` is complete
  and measured, while writable providers, other historical clock APIs, and
  filesystem timestamps are later 1.x work; and
- the 1.0 utility inventory remains deliberately small and is selected only
  after the retained system facilities are complete; the backlog list is
  candidate inventory and suitably licensed existing utilities may satisfy the
  final selection; and
- 1.0 preserves and permits inspection or change of the ordinary read-only,
  system and archive attribute bits, enforces read-only, treats archive as
  metadata only, and defers enhanced system-file visibility across user areas.

### Stage 4 — Normalize disk state

Architecture Specification 28 defines the authoritative model for physical
records, self-contained normalized logical bindings, saved cold-boot state and
observed/derived state. The BIOS-owned records are operational authority; FDB
identity is provenance. Validated synchronous transitions, explicit dependency
invalidation, managed capability removal, media-state separation, DUP/SYSGEN
requirements and CONFIG H's verified but not power-failure-atomic persistence
contract are frozen. The source audit is recorded in
`docs/engineering/STAGE-4-DISK-STATE-SOURCE-AUDIT.md`. Stage 4 is complete.

### Stage 5 — Define the bounded 1.0 PDS

Architecture Specifications 18 and 29 define the fixed 192-byte PDS and its one
1.0 owner, built-in command history. The existing PDS ABI 1 descriptor is
sufficient; RSX/CPX profiles, disk/configuration state, the derived service
registry, stacks and workspaces retain their natural owners. Cold/warm/reset
rules, fixed capacity, failure behavior and the exact 53 KiB record-aligned COM
ceiling are frozen. Engineering Specification 152 records the source audit and
the focused remaining cold-boot initialization task. General allocation,
migration, configurable sizing and runtime expansion are deferred. Stage 5 is
complete.

### Stage 6 — Freeze extension and clock interfaces

Architecture Specifications 20, 22 and 25 freeze the CPX, RSX,
resident-service, private-BDOS and native-clock interfaces. BetterCP/M owns
176-196 for production, reserves 197 as an undefined future escape, and uses
198-199 only for non-public tests. Final production assignments occupy
176-183. Historical P2DOS Functions 200/201 remain outside the private range
and are supplied by an optional-to-load but required-to-ship `P2DOS.RSX`.

Function 182 retains the existing 20-byte callable-service ABI, operation and
status definitions. The bounded PDS owns no registry state. The native `TIME`
ABI retains its canonical five-byte record and complete GET/SET validation
contract. Original P2DOS behavior establishes A=00h and HL=0000h success;
BetterCP/M defines FEh/00FEh for an installed frontend's claimed failure and
FFh/00FFh when the frontend is absent. Test-only selectors remain outside the
frozen application ABI.

After `P2DOS.RSX` is complete and qualified, measure the incremental cost of
two mutually exclusive BDOS 104/105 frontends. The four-byte profile implements
the CP/M 3/DOS+ 2.5 record and returns seconds in A; the five-byte profile
implements the Z80DOS 2.4 record and returns A=00h. They are optional 1.0
candidates, not release gates. They may be included only if they remain small,
stateless adapters over TIME and require no Function-12 impersonation, new
lifecycle architecture, filesystem timestamps, or other originating-system
behavior. No frontend may infer a caller's buffer convention heuristically.

A separate optional-to-load `P2DOS.RSX` frontend intercepts Functions 200/201
and consumes the native `TIME` service; it contains no hardware driver and
resolves TIME anew for every call. Both required 1.0 providers may
remain read-only; Function 201 maps native SET_UNSUPPORTED through the
frontend. Other historical frontends may later consume the same native
service without modifying or duplicating a hardware provider.

Stage 6 is complete. Actual selector migration, fallback changes, client
rebuilds, P2DOS.RSX implementation and executable qualification belong to the
implementation program. Engineering Specification 153 records the source audit
and the non-obvious migration cases.

### Stage 7 — Publish retained implementation contracts

Turn the reduced boundary into implementation-ready acceptance specifications

release tooling. Reject any design that implicitly restores a deferred feature
as a prerequisite. The ROM profile follows Architecture Specification 27:
ownership precedes placement, lifetime precedes allocation, and mutable live
objects are instantiated in RAM from immutable templates.

implementation gaps. Engineering Specification 156 records the bounded erratum
which limits 1.0 to explicit profile order and relationships its frozen carriers
actually represent; general declarative dependency metadata remains future
carrier work. The audit found no architectural blocker. Stage 7 is complete.

## Post-1.0 architectural review

Immediately after 1.0, conduct a measured retrospective whose **primary
objective is increasing usable TPA**. The 1.0 unloaded 53 KiB baseline is the
reference, not the desired post-1.0 ceiling. Establish achievable higher-memory
milestones from measurements rather than assigning an unsubstantiated target.
This review does not change the released 1.0 architecture or delay its validation.
The approaches below are illustrative starting points, not an exhaustive list
or a prescribed solution. Expand the investigation wherever evidence suggests
other worthwhile ways to increase usable memory; compare alternatives rather
than treating the initial suggestions as locked design commitments.

Evaluate more efficient implementations, shared routines and services, avoidable
code/data duplication, fragmentation, reserved workspace and state lifetimes.
Assess each feature's memory cost and benefit so features and redesign work can
be prioritized. Consider moving suitable core features into optional unloadable
RSXs, splitting command-only support into reclaimable CPXs, or using other
placement mechanisms where justified. No feature is presumed suitable for
relocation merely because it is large.

For every candidate, record permanent code/data and reserved workspace, loaded
and peak scratch costs, net TPA recovered after replacement machinery, default
and optional loaded configurations, execution/I/O costs, frequency of use,
compatibility consequences and failure/recovery behavior. Rank alternatives by
actual usable-memory gain and practical value, not source-code size alone.
Account for loader, dispatch, dependency, reconstruction and retained-state
costs. Loading and unloading optional services must have explicit measured TPA
results. Feature removal or changed guarantees require an explicit proposal.

A **central part of the assessment is a source-backed examination of Z-System**:
how did its implementations balance feature coverage, resident memory and TPA,
and which techniques can BetterCP/M adopt? Investigate code sharing, module
placement, reclaimability, service dispatch, installation/removal and reload.
The earlier question about smaller resident management without BetterCP/M's
overlay machinery is a research question to establish from sources, not an
assumed equivalence of functionality or guarantees. Identify the versions and
configurations being compared.

Compare equivalent functionality and account separately for code, reserved
workspace, transient utilities, reclaimable command memory, ROM/banked storage,
and usable TPA. Examine relocation, dependency handling, WBOOT reconstruction,
and failure recovery. Distinguish the cost of required guarantees from avoidable
implementation overhead or duplication.

Use the 15 manager-helper slots consolidated in R3PACK.RSX as concrete evidence:
measure combined disk/code size, live memory and scratch requirements, disk reads
and latency per operation, required-media dependencies, and failure paths.
Evaluate simplifying or eliminating overlays as well as broader use where it
actually increases usable TPA. The fixed 1 KiB CONFIG control-overlay limit and
any compaction/caller-validation choices made to preserve it are also evidence.
Produce measured alternatives and prioritized recommendations, with memory
improvement as the organizing objective. This remains post-1.0 work.

Before full 2.0 design, use that evidence and experience from bounded later-1.x
ports to reassess memory placement, workspace lifetime and overlay organization,
ROM execution, PDS allocation, banking, firmware and device services,
CONFIG/FDF/installation boundaries, and platform interfaces together. Preserve
the 53 KiB TPA evidence, and do not turn the bounded RomWBW 1.1/1.2 port into an
implicit architectural redesign.

### Model 4 upper-RAM recovery and target build profiles — 2026-10-23

Maintainer decision: retain Model 4 upper-RAM recovery as a post-1.0
investigation to revisit after the first full-RAM cpmsim prototype. Engineering
Assessment Part 4 is approved; the next bounded part is an isolated cpmsim
prototype and its measured checks, followed by another review pause.

The current Model 4 layout reserves F400h–FFFFh for the keyboard interface
(1 KiB) and video RAM (2 KiB). These devices overlay ordinary RAM rather than
representing missing physical RAM. MM CP/M provides a comparative example:
normally expose full RAM, briefly map in the keyboard/video window for hardware
access, then restore the RAM mapping. Display refresh continues independently
of whether the CPU can address video RAM.

Assess a Model 4 platform binding with explicit mapping transitions and
resident placement that keeps executing code and every accessed byte visible
throughout those transitions. A minimal leaf access stub may keep its stack
in hidden upper RAM if it performs no stack operations while the window is
selected and interrupts/NMI cannot access that stack; restore RAM before RET.
Include the built-in console,
M4SCRN.RSX and its BIOS cursor-state bindings, callbacks, interrupts/NMI,
bootstrap loading, warm boot, disk-error paths and recovery. Hardware mapping
must remain a platform responsibility. A uniform upward address shift is not
sufficient.

Use common sources with explicit target build profiles and consistent artifact
identities. Qualify full-RAM cpmsim first; do not make its layout inherit the
Model 4 adapter's present ceiling. The Model 4 mapping prototype is a later,
separately qualified step. Preserve ordinary application and supported service
interfaces while rejecting mismatched private helpers and address-bound modules.

Measure net TPA recovery after all added code, state, stack, alignment and
compatibility-check costs. Track unloaded maximum, shipped startup and future
defaults including NDR and datestamping, plus temporary transaction headroom.
The 3,072-byte window is a gross opportunity, not a promised net gain.
The accepted core 1.0 baseline remains

## VT52 monitor scope correction — 2026-10-15

**Required for BetterCP/M 1.0: reimplement VT52.RSX as VT52 monitor support.**

The intended relationship is the same as ADM3A.RSX: a CP/M program configured
for the terminal sends its screen commands, and the provider makes the
BetterCP/M console perform those terminal operations. The same VT52.RSX must work across hardware with a VT52-capable console.
Any hardware-specific adaptation belongs in the BIOS/backend. This portable
terminal role must not be confused with embedding Model 4 rendering inside the
RSX. ADM3A.RSX does not implement VT52.

The current VT52.RSX is instead a cpmsim VT52-to-ANSI adapter. Its translation
and application tests do not fulfill this requirement. ANSI.RSX remains the
separate provider for its documented ANSI/VT100 subset; this correction does
not establish complete VT100 emulation as a new commitment.

Required work:

- Align the VT52 engineering contract, implementation, backend coverage and
  developer/user documentation with the intended monitor-support role.
- Implement and qualify the accepted VT52 behavioral scope, with one portable
  VT52.RSX for systems exposing a VT52-capable console. Hardware-specific screen
  adaptation belongs in the BIOS/backend, not separate per-machine VT52 RSXs.
  Document backend requirements explicitly; ANSI translation
  must not stand in for the complete monitor-support requirement.
- Update VT52TST and its qualification to exercise the corrected provider and
  verify positioning, erasure, input/replies and lifecycle behavior within the
  accepted scope. Preserve the existing adapter evidence as historical evidence.
- Retain the single-active-monitor contract, RSX unloadability and recovery of
  the 53K unloaded TPA. Audit any required shared/backend changes before adding
  permanent resident code.
- Update target packaging and rerun exact-artifact platform, application and
  distribution qualification before declaring VT52 complete.

This reopens the VT52 implementation item despite the earlier System Disk
completion milestone. It does not reopen general TCAP, simultaneous monitor
