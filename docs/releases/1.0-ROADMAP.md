# BetterCP/M 1.0 Roadmap

## Status and authority

This is the canonical ordering of the remaining BetterCP/M 1.0 work. The
project backlog records individual tasks, architecture documents define
accepted contracts, and engineering specifications record implementation and
qualification evidence. None of those lists may silently reorder this roadmap
or collapse an architecture stage into its later implementation work.

Stages 1 and 2 established the project-wide ABI design conventions and the
resident-service ABI/registry. Stage 3 is the current critical path. Stages 4
through 8 remain explicit design stages that precede the corresponding
implementation program.

## Architectural critical path

### Stage 3 — Complete stateful RSX reconstruction

Finish the Function 202 transaction coordinator, persistent profile
publication, resolver restoration, and cross-platform qualification. Forced
relocation must preserve declared mutable state and internal pointers; a
failed transaction must leave the live profile unchanged.

### Freeze the final 1.0 boundary

After Stage 3, reconcile and approve the remaining release boundary before
opening another architecture front. The already frozen constraints include:

- trs80gp/Model 4 and z80pack/cpmsim are the two 1.0 targets;
- the default configuration retains at least 53 KiB usable TPA;
- the 1.0 ROM profile executes immutable code in place under enforced write
  protection, with all mutable state in RAM;
- terminal-capability redesign is post-1.0;
- a bounded single-bank RomWBW/HBIOS port is a 1.1 or 1.2 candidate; and
- generalized bank-aware firmware and full RomWBW integration are 2.0 work.

### Stage 4 — Define HISTORY.RSX

Define its callable service, owned state, reconstruction class, lifecycle, and
relationship to persistent command input. Specify warm-boot behavior and how
history survives resident-layout changes. The existing fixed PDS history
buffer is an implementation baseline, not the final architecture.

### Stage 5 — Define PATH semantics

Define named-directory resolution, canonical `DU:` storage, lookup order,
current drive/user interaction, failure behavior, and the boundary between
CCP, transient utilities, NDR management, and common resolver services.

### Stage 6 — Normalize disk state

Define one authoritative model for physical-drive properties, logical-drive
bindings, active state, saved cold-boot state, and session state. Reconcile
that model with FDF source definitions, compiled FDB descriptors, CONFIG,
BIOS, DUP, SYSGEN, and installation. Define capability requirements,
validation, invalidation, and failure behavior before implementing those
consumers.

### Stage 7 — Define the PDS allocator ABI

Derive the allocator from measured requirements for the resident-service
registry, reconstruction records, HISTORY, PATH/NDR, normalized disk state,
configuration state, and every other accepted 1.0 owner. Define discovery,
ownership, allocation, versioning, migration, current/next-boot sizing, and
failure behavior while preserving the 53 KiB TPA floor.

### Stage 8 — Reconcile and publish the architecture

Reconcile architecture documents, engineering specifications, programmer
guides, the backlog, and the approved 1.0 scope. Resolve obsolete or
contradictory text and publish implementation-ready specifications for Stages
4 through 7. This is an architecture gate before broad implementation; it is
separate from final user manuals, release notes, and packaging documentation.
Chat should perform the bulk documentation reconciliation to conserve Codex
credits for engineering and implementation. Codex remains responsible for
source-derived technical verification, repository-specific corrections, and
any executable or generated evidence needed to make the reconciled text
authoritative.

## Implementation program

Implementation begins after Stage 8 and follows the accepted specifications:

1. Finish and qualify the core, PDS implementation, and 1.0 ROM profile.
2. Implement named directories, PATH, NDR, and CCP command integration.
3. Implement HISTORY and finalize CCP, CPX, RSX, command-input, and batch
   architecture.
4. Implement FDF/FDB against the normalized disk-state model.
5. Complete CONFIG, DUP, SYSGEN, installation, and platform work.
6. Complete attributes, clocks, timestamps, and required compatibility work.
7. As the final design decision, define the accompanying 1.0 utility and disk
   inventory.
8. Implement or adopt the selected utilities, assemble the distribution,
   complete release documentation, and run full release qualification.

The utility inventory deliberately remains the final design decision. Further
machine surveys, the 2.0 bank architecture, terminal-capability redesign, and
the future mixed-track FDF/FDB extension remain at their assigned post-1.0
decision points unless a required 1.0 target demonstrates a blocking need.

## Continuous acceptance gates

Every implementation increment must preserve the accepted ABI boundaries,
remain buildable for both 1.0 targets, and retain at least 53 KiB usable TPA in
the default configuration. ROM-profile work must ultimately pass actual
execution-in-place testing with enforced write protection. Compatibility and
memory evidence are collected continuously rather than deferred until release
assembly.
