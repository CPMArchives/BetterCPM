BETTERCP/M CLOCK PROVIDER AND TIME-SERVICE ABI
==============================================

Status: adopted BetterCP/M 1.0 design. This specification supersedes the
combined `P2DOS.MAC + CLKHW.INC` provider model. The existing callable `TIME`
ABI, FreHD and z80pack providers, and native TIME.COM already implement the
principal runtime separation defined here.


1. PURPOSE AND INVARIANTS
-------------------------

BetterCP/M separates clock hardware, its native clock service, native clients,
and optional historical interfaces at runtime. The architecture preserves two
invariants:

  * adding a clock API or compatibility frontend shall not require modifying
    or duplicating the hardware implementation; and
  * adding a clock device shall not require modifying every clock frontend.

The layers are:

  hardware provider  coherent device access and native-record translation
  native TIME ABI    hardware-independent BetterCP/M callable service
  native consumer    TIME.COM and other BetterCP/M software
  optional frontend  P2DOS or another separately specified historical API

The hardware provider and native TIME service are currently one BRSX-v2
module. That is a valid implementation of two architectural layers: the module
advertises the native service and contains the device-specific implementation.
It does not also become every historical frontend.

BDOS supplies only mechanical routing and unsupported-call behavior. Human
presentation remains in consumers.

The generic resident-service resolver is infrastructure, not another clock
layer. The native execution path is:

  TIME.COM
      |
      | resolve `TIME` ABI 1.0 through Function 208/182
      v
  current callable TIME provider
      |
      v
  clock hardware

The P2DOS execution path is:

  P2DOS application
      |
      | Function 200 or 201
      v
  P2DOS.RSX
      |
      | resolve `TIME` ABI 1.0 through Function 208/182
      v
  current callable TIME provider
      |
      v
  clock hardware


2. CANONICAL NATIVE CLOCK RECORD
--------------------------------

TIME ABI 1.0 uses this five-byte record:

  +0  byte  little-endian day-count low byte
  +1  byte  little-endian day-count high byte
  +2  byte  packed-BCD hour, 00h through 23h
  +3  byte  packed-BCD minute, 00h through 59h
  +4  byte  packed-BCD second, 00h through 59h

Day 1 is 1 January 1978 and day 65535 is 5 June 2157. GET publishes the record
only after obtaining and validating one coherent sample. SET validates the
complete record before changing the clock.

The record represents the machine's ordinary local civil time. ABI 1.0 defines
no timezone, daylight-saving, subsecond, alarm, scheduler, or network-time
model.

This representation originated with P2DOS, but BetterCP/M adopts it as its
native clock record because it is compact, adequate, historically established,
efficient for common RTCs, and already implemented by the qualified providers.
P2DOS compatibility is a useful consequence rather than the purpose of the
native service. A competing or larger native record requires a demonstrated
need and an appropriate ABI version change.


3. NATIVE TIME SERVICE
----------------------

A provider advertises service ID `TIME`, ABI 1.0, through the resident-service
registry. Clients discover its callable address through the resident-service
gateway. Function 208 is the current gateway number; Architecture Specification
20 assigns Function 182 as its final 1.0 number when Stage 6 migrates private
selectors. The service identity and ABI do not change with that gateway-number
migration.

The TIME request block is ten bytes:

  +0  byte  structure version = 1
  +1  byte  structure length = 10
  +2  byte  operation: 0 GET, 1 SET
  +3  byte  request flags; zero in ABI 1.0
  +4  5     canonical clock record
  +9  byte  reserved; zero in ABI 1.0

On successful GET, the provider writes the record at +4 and returns A=0 and
HL=request+4. On successful SET, it returns A=0; SET details shall be completed
when a writable provider is qualified. On failure, A contains a TIME-ABI status
and HL is zero. DE remains the request address and SP, IX, and IY are preserved.

The implemented TIME ABI 1.0 status values are:

  00  SUCCESS
  01  BAD_REQUEST_VERSION
  02  BAD_REQUEST_LENGTH
  03  BAD_OPERATION
  04  BAD_FLAGS_OR_RESERVED_FIELD
  05  UNAVAILABLE_OR_HARDWARE_FAILURE
  06  INVALID_CLOCK_RECORD
  08  SET_UNSUPPORTED

Status 07 is unassigned. These native statuses are distinct from the deliberately
smaller public result convention of `P2DOS.RSX`.

Capability bit 0001h advertises SET. A read-only provider omits that bit and
returns SET_UNSUPPORTED for operation 1. Zero or one provider of `TIME` ABI 1
may be active. Duplicate service identity is rejected through the ordinary
resident-service rules before publication.

A resolved callable address is valid only for the resident-layout generation
in which it was returned. Clients rediscover after reconstruction according to
Architecture Specifications 20 and 21.

The service ID, ABI version, capabilities, and provider module identity are
stable descriptions. A returned callable address is disposable runtime state;
diagnostics and configuration shall not treat that address as provider identity.


4. HARDWARE PROVIDER CONTRACT
-----------------------------

A hardware provider owns:

  * coherent hardware reads;
  * optional hardware writes;
  * device-specific errors and bounded waits;
  * conversion from device representation to the canonical record; and
  * conversion from the canonical record when SET is supported.

It does not own historical API selectors, command syntax, human-readable
formatting, or CCP prompt policy.

Hardware may expose BCD calendar registers, binary fields, an epoch counter,
emulator host-time services, or another representation. The provider absorbs
that difference. It shall not fabricate plausible time after an unavailable,
invalid, or torn sample.

`FREHDCLK.RSX` supplies `TIME` through the FreHD extended-command interface and
serves real FreHD hardware and trs80gp's FreHD emulation. `ZPRTC.RSX` supplies
the same ABI through z80pack/cpmsim ports 25 and 26. Both required 1.0 providers
may remain read-only. Their engineering specifications define their exact
coherence, range, error, and memory behavior.


5. NATIVE CONSUMERS
-------------------

TIME.COM discovers and calls the native `TIME` service. It does not require a
historical compatibility frontend. It owns command syntax, input parsing,
calendar conversion, formatting, help, and human-readable errors.

The minimum 1.0 interface is:

  TIME             display the current local date and time
  TIME /PROVIDER   identify the installed provider

The 1.0 utility work includes a native SET request path even though the required
providers may be read-only. Exact human SET syntax belongs to the utility
specification rather than this provider ABI.

A future CCP clock display or other native client likewise uses `TIME`
directly. No such prompt feature is added to the 1.0 scope by this architecture.


6. P2DOS COMPATIBILITY FRONTEND
-------------------------------

P2DOS compatibility is supplied by the separate, optional `P2DOS.RSX`
frontend. The shipped 1.0 compatibility component owns:

  C  = 200   P2DOS GET TIME
  DE = address of its writable five-byte record

  C  = 201   P2DOS SET TIME
  DE = address of its five-byte record

For every request, the frontend preserves the caller's buffer address, resolves
the native `TIME` service through the defined lower-service path, invokes the
returned address immediately, translates the result, and discards the address.
It shall not retain a callable TIME address across service invocations or
resident-layout generations. This rule avoids another rebinding mechanism.

Because the P2DOS and native records match, ordinary data translation is
pass-through. The frontend contains no hardware driver. Its eventual measured
allocation is implementation evidence, not part of this ABI.

The public P2DOS-facing contract needs only SUCCESS, UNAVAILABLE,
SET_UNSUPPORTED, and OPERATION_FAILED. Exact success register behavior and the
non-FFh result values remain a Stage-6 closure item pending source or executable
evidence. Native validation and hardware statuses collapse into those public
outcomes; no elaborate public error taxonomy is required.

If no frontend intercepts Function 200 or 201, the call reaches BDOS. BDOS
mechanically returns 0FFh for either selector. This means that the P2DOS
interface is not installed; it does not mean that the native clock is absent.
A fully functional native TIME provider may still be loaded.

Conversely, `P2DOS.RSX` may be installed while no native TIME provider is
available. The frontend maps that resolver failure to its documented
UNAVAILABLE result. BDOS does not locate providers, inspect records, access
hardware, or distinguish any other cause.

A read-only provider does not remove Function 201 from the frontend. The
frontend maps the native SET_UNSUPPORTED result to its documented public result.
Native clock use remains complete without loading this frontend.

The default configuration need not load `P2DOS.RSX`. `FREHDCLK.RSX` or
`ZPRTC.RSX` alone supplies native clock service for TIME.COM and other native
consumers. Loading `P2DOS.RSX` adds historical clock-call compatibility without
changing or duplicating the provider.


7. OTHER HISTORICAL FRONTENDS
-----------------------------

Two BDOS 104/105 clock-call profiles are bounded optional 1.0 candidates after
`P2DOS.RSX` is complete and measured. They are not release requirements:

  * the CP/M 3 and DOS+ 2.5 profile uses a four-byte day-count/hour/minute
    record, returns seconds in A on GET, and resets seconds to zero on SET;
  * the Z80DOS 2.4 profile uses a five-byte day-count/hour/minute/second record
    and returns A=00h on GET.

The profiles cannot be autodetected safely because the call carries no buffer
length and callers do not identify their expectation consistently. A five-byte
GET can overwrite a four-byte caller. If implemented, separate mutually
exclusive frontends shall resolve and invoke TIME anew for every request, keep
no provider pointer, use private translation scratch, and leave Function 12
unchanged. Working binary names are `T104C3.RSX` and `T104Z8.RSX`; the names
describe clock-call conventions rather than broader operating-system support.

Their inclusion is decided only after the required `P2DOS.RSX` establishes the
actual common code, resident cost, lifecycle behavior, and qualification cost.
They may ship only if they remain small stateless adapters requiring no new
TIME semantics, lifecycle architecture, operating-system impersonation, or
filesystem timestamp behavior. They remain absent from the default profile and
are not 1.0 release gates.

Later ZSDOS/ZDDOS, DateStamper, or other adapters may consume the same native
TIME service. Each frontend owns its historical selector or entry convention,
record translation, compatibility statuses, and required validation. None
duplicates the device driver. Clock-call compatibility does not imply
timestamp-layout compatibility or broader emulation of the corresponding
operating system; those larger facilities remain later 1.x work.


8. CANONICAL DATA AND LATER TRANSFORMATIONS
-------------------------------------------

TIME ABI 1.0 exposes only the canonical five-byte record. It does not provide
Gregorian structures, strings, locale policy, or presentation operations.
Transient consumers may share conversion source without imposing resident code
on every system.

The architecture leaves room for later neutral transformations such as:

  day count -> year/month/day
  year/month/day -> day count

No operation numbers, request blocks, service IDs, memory allocation, or release
commitment are reserved for them now. If measured use by multiple resident
clients later justifies shared runtime code, the resident-service registry can
host a separate optional stateless conversion service. That is preferable to
requiring every hardware provider to implement or forward calendar conversion.
A TIME ABI revision remains possible if a demonstrated requirement instead
shows that the transformation belongs inseparably to clock provision.

The broader provider rule is:

  Providers normalize hardware into the smallest stable domain record.
  Compatibility adapters translate at API boundaries. Shared neutral
  transformations become a service only when measured runtime sharing justifies
  their resident cost. Presentation remains with consumers.

Runtime decoupling takes precedence over source deduplication, but resident
abstraction is not introduced merely to avoid duplicated source code.


9. SUPERSEDED SOURCE-COMPOSITION MODEL
--------------------------------------

The standard architecture does not build each frontend by combining a common
service body and hardware include:

  P2DOS.MAC + CLKHW.INC -> hardware-specific P2DOS provider

That arrangement remains technically possible for a constrained private build,
but it ties hardware to one frontend and duplicates hardware code when several
frontends coexist. BetterCP/M 1.0 instead ships independently built hardware
providers and the separate `P2DOS.RSX` frontend. A hardware porter implements the
native `TIME` ABI once.


10. QUALIFICATION
-----------------

Native-service acceptance covers:

  * correct TIME discovery, version, capabilities, and request validation;
  * one TIME.COM binary operating unchanged with every qualified provider;
  * known dates, BCD validation, range limits, and coherent rollover sampling;
  * read-only SET, invalid input, hardware failure, and unavailable hardware;
  * provider load, unload, movement, WBOOT, and rediscovery;
  * rejection of duplicate TIME providers before publication; and
  * unchanged unrelated hardware or emulator state.

P2DOS-frontend acceptance additionally covers:

  * exact historical entry and successful-return behavior;
  * mechanical 0FFh fallback when the frontend is absent;
  * native-to-public result mapping, including read-only SET;
  * operation with each qualified hardware provider; and
  * frontend load/unload without changing or duplicating the provider;
  * per-call lookup through the lower-service path; and
  * proof that no callable address survives an invocation or reconstruction.

The exact P2DOS success convention and remaining public result values are a
Stage-6 design-closure gate. Other historical frontends and filesystem
timestamps are outside 1.0 qualification.
