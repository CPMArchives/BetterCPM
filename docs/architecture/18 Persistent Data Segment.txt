BETTERCP/M PERSISTENT DATA SEGMENT

Status: accepted BetterCP/M 1.0 architecture and later 1.x direction.


1. NAME AND PURPOSE

The protected high-memory data region is the Persistent Data Segment (PDS).
"Persistent memory" and "persistent data" may be used descriptively, but PDS
is the architectural name.

The PDS holds writable state whose ownership contract requires PDS discovery,
versioning and preservation across command-environment reconstruction and
ordinary warm boot.  The PDS is not BetterCP/M's general .bss.  Writability,
physical adjacency or residence above the TPA does not establish PDS ownership.
Fixed subsystem state, stacks and temporary workspaces retain their own owners.


2. BETTERCP/M 1.0 BOUNDED PROFILE

BetterCP/M 1.0 has exactly one PDS owner: the built-in command-history facility.
The fixed PDS occupies D504h through D5C3h, 192 bytes total:

  Offset  Size  Meaning
     0       2  signature "BH"
     2       1  structure version, currently 1
     3       1  packed-record count
     4       2  packed bytes used, little endian
     6       4  owner-private working state; no persistent semantics
    10     182  length-prefixed packed command records

The four working bytes are reserved to the history owner.  A reader must not
interpret them as allocation-directory entries, global metadata or a promise
that their runtime values survive initialization or reconstruction.  The
history owner initializes them before each relevant use.

The existing version-1 Extension Control Block is the complete 1.0 discovery
contract.  Its valid flag and published lower boundary identify the fixed PDS;
the system gateway supplies the upper boundary.  Current and boot sizes are
both 192 bytes.  Version 1 needs no heap, owner directory, allocation table,
migration service, configurable size or runtime growth mechanism.


3. OWNERSHIP EXCLUSIONS

The following writable objects remain outside the 1.0 PDS:

  * the RSX reconstruction profile, which is fixed extension-subsystem state;
  * the CPX reconstruction profile, which is fixed gateway state;
  * a future startup-command executed flag, which belongs to the gateway;
  * the resident-service registry, which is derived from loaded modules;
  * normalized disk and configuration state, which is fixed BIOS/disk state;
  * optional clock-provider state, which belongs to its provider RSX;
  * stacks; and
  * temporary or statically overlaid workspaces.

These exclusions are semantic.  A future ROM/RAM layout may move their physical
addresses without converting them into PDS allocations.


4. INITIALIZATION AND LIFECYCLE

Cold boot creates an empty version-1 history object.  Warm boot, CCP and CPX
reconstruction, and RSX layout changes preserve the valid object byte for byte.
The history owner validates the signature and version before use.  An invalid
or unknown history header is reset to a valid empty version-1 object; no caller
may consume its record area first.

Ordinary command insertion may change count, used length, working bytes and
packed records within the 192-byte allocation.  It may evict the oldest whole
record when required.  It may not grow beyond the published PDS boundary.
Failure to add one command leaves the segment valid and must not impair the CCP.

The current source validates or resets history when the reconstructed CCP
starts.  Its cold gateway entry does not yet force a previously valid object to
empty.  Making cold boot perform that unconditional initialization is a 1.0
implementation task, not a reason to enlarge or redesign the PDS contract.


5. CAPACITY AND TPA

The PDS lower boundary is D504h and the exclusive TPA ceiling is D501h.  A COM
program therefore has 54,273 addressable bytes beginning at 0100h; the largest
complete 128-byte-record image is 54,272 bytes, exactly 53 KiB.  This is the
accepted default 1.0 floor.  Any later layout work must retain that loadable
record capacity or receive an explicit release-scope decision.


6. LATER 1.x DIRECTION

A later release may replace this fixed bridge with a general owner-scoped PDS
allocator.  That work may define allocation metadata, discovery, migration,
release policies, configurable cold-boot sizing and controlled expansion using
the stateful reconstruction transaction.  It must begin from measured consumers
rather than treating all resident writable data as PDS state.

Possible later consumers include state that must survive unloading of its
implementing module.  Optional feature state normally remains in that feature's
RSX, and fixed disk, BIOS, gateway and reconstruction data remain with their
subsystems unless a separately approved lifetime contract demonstrates a need
for PDS ownership.

This later direction creates no 1.0 ABI promise about allocator format,
granularity, maximum size or allocation identifiers.
