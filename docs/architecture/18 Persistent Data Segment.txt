BETTERCP/M PERSISTENT DATA SEGMENT

Status: architectural design baseline; general allocator and resizing pending.


1. NAME AND PURPOSE

The protected high-memory data region is the Persistent Data Segment (PDS).
"Persistent memory" and "persistent data" may be used descriptively, but PDS
is the architectural name.

The PDS holds writable system state which must survive transient execution,
CCP/CPX reconstruction, and ordinary warm boot. Persistence across power-off
requires an explicit system-track or file save operation. Cold boot creates a
new PDS from saved configuration and initialized defaults.


2. PLACEMENT AND GROWTH

The PDS has a fixed upper boundary immediately below the immutable core and a
lower boundary which may grow downward:

  BIOS and BDOS core
  fixed BetterCP/M system gateway
  PDS, fixed top and downward-growing lower boundary
  installed RSX chain
  dynamic CP/M compatibility gateway
  CPX chain
  CCP
  TPA

Expanding the PDS adds addresses below its former lower boundary. Existing PDS
allocations do not move. Code must discover the PDS through the published
descriptor rather than compile a private base address.

The physical PDS high-water mark may increase but may not decrease between
cold boots. Releasing an allocation makes it reusable inside the PDS; it does
not move the resident boundary upward. A smaller boot configuration becomes
effective only when cold boot rebuilds the segment.

The system distinguishes:

  PDS_CURRENT_SIZE   physical allocation in the running system
  PDS_BOOT_SIZE      configured allocation for the next cold boot

A larger boot setting may be applied immediately through controlled expansion.
A smaller setting remains pending and reports that cold boot is required.


3. OWNERSHIP AND ALLOCATION CONTRACT

The PDS is one contiguous system-owned resource. XPM.RSX or another adjacent
second class of persistent memory is rejected. Components which genuinely need
PDS storage request it through one allocator and do not claim raw addresses
independently.

The PDS contains mandatory system infrastructure and owner-scoped allocations
whose lifetime must be independent of a loaded module. Optional resident
features normally own their state in the RSX which implements them. The test is:

  If unloading a feature should logically make its data cease to exist, that
  data belongs to the feature rather than the PDS.

Consequently, command-history records belong to HISTORY.RSX and named-directory
definitions to NDR.RSX. Security, batch and flow state are likely candidates
for the resident modules which implement those facilities, but remain subject
to their individual designs. The user pays optional protected-RAM cost only
while the feature is installed. A CPX must never own indispensable persistent
state because a transient program may overwrite the CPX region.

An RSX may instead request an owner-scoped PDS allocation when its data must
survive explicit unloading, replacement, or absence of the module. This is an
exception selected by lifetime, not the default storage model for optional
features.

Every allocation records at least an owner/facility identifier, structure
version, length, active/free state, alignment if required, and reset/lifetime
policy. Consumers obtain an allocation through the stable PDS interface and
must not retain pointers into reclaimable CCP, CPX, or transient memory.

Unloading a component defines whether its allocation is released, retained for
reload, or migrated. Warm boot preserves allocations according to their stated
policy. Explicit reset may clear selected structures without contracting the
PDS. Cold boot validates or initializes every configured structure.


4. RESIDENT FEATURE SERVICES

An RSX may provide a callable service to the CCP or another system component;
it need not exist solely to intercept a BDOS call. This permits optional CCP
features such as command history and named-directory resolution to keep their
code and data resident without enlarging the permanent CCP or base PDS.

Each callable resident service publishes a small versioned record containing
at least a service identifier, ABI version, current entry address and capability
flags. The PDS holds the service registry because it is core reconstruction
metadata, not feature data. Resident-layout reconstruction updates registered
entry addresses. Clients must rediscover a service after reconstruction, or
call it through a stable gateway; they must not retain an untracked raw pointer
to a movable RSX.

The CCP detects these services during initialization and after reconstruction.
If HISTORY or NDR is absent, the corresponding command-environment feature is
unavailable without impairing the base CCP. Explicitly unloading an ordinary
stateful service discards its state. HISTORY may therefore discard its history,
and NDR may discard its live register and later rebuild it from an NDR file.

The first implementation target is an ordinary STATEFUL RSX whose code and data
move together and cease to exist on explicit unload. Copying bytes alone is
insufficient when the live image contains absolute pointers created after load;
such pointers must be forbidden, represented as relocatable offsets/handles, or
declared for adjustment. A later STATE_PRESERVING service may serialize or
migrate state through a versioned contract or an owner-scoped PDS allocation.


5. CONTROLLED RUNTIME EXPANSION

An ordinary allocation request never expands the PDS implicitly. Insufficient
space returns a defined failure. Expansion is a deliberate system reconfiguration
performed primarily by transient code, such as CONFIG.COM or a dedicated
rebuilder.

PDS expansion uses the resident-layout reconstruction transaction defined by
the Extension Architecture. It introduces no separate relocation or active-
state problem: removing a higher RSX already requires every lower RSX and the
command environment to be rebuilt at new addresses. PDS expansion merely
changes the boundary supplied to that same operation.

Preparation occurs while the resident environment is intact:

  1. inspect the current layout and requested size;
  2. inventory loaded RSXs and CPXs;
  3. validate their declared reconstruction and state requirements;
  4. load required images and relocation information;
  5. preserve explicitly supported state;
  6. calculate and validate the complete new layout; and
  7. reject overlap with the rebuilder, its workspace, or the minimum TPA.

The short commit phase then quiesces the environment, rebuilds extensions at
their lower addresses, enlarges the PDS, restores or initializes supported
state, moves the dynamic gateway, updates page zero and the system descriptor,
and reconstructs the command environment.

The STATELESS, STATEFUL, STATE_PRESERVING, and COLD_ONLY behaviors are the
general RSX reconstruction contract; they apply equally to load, unload,
compaction, and PDS resizing.

Most reconstruction machinery belongs in transient code. Permanent code
publishes layout and allocator interfaces and supplies only the irreducible,
short commit mechanism. Preparation should finish disk I/O before commit so a
partly rebuilt resident environment is not required to load its own components.


6. CONFIGURATION, SIZING AND TPA POLICY

CONFIG displays current and next-boot PDS sizes. Saving the boot size is
independent of saving unrelated live drive formats or other settings. Runtime
growth must fail cleanly if the proposed boundary overlaps the rebuilder or
violates the configured minimum TPA, unless the user deliberately selects a
profile with a smaller TPA.

PDS size is a user-selectable memory trade-off. The number and geometry of
logical drives dominate required capacity; a user selecting more or larger
independently configured drives selects a larger PDS and accepts the resulting
reduction in TPA.

The working sizing targets are:

  1 KiB       minimum constrained profile and goal for a four-drive base
  1.25 KiB    current preferred default planning target
  1.5 KiB     fallback default if the final ABI leaves inadequate reserve
  larger      user-configured drive and system profiles

Allocation should use 256-byte pages unless measurement establishes that a
finer granularity has a material benefit. These are budgets and capacities,
not fixed ABI partitions.

The expected four-drive base inventory is approximately:

  623 bytes   current drive tables and disk session state
   64 bytes   search path capacity
   82 bytes   current RSX and CPX reconstruction records
 48-64 bytes PDS descriptor and allocator metadata
 40-48 bytes core settings and canonical date/time state
 143-167     alignment and growth reserve within a 1 KiB profile

This makes a 1 KiB base plausible but tight. A 1.25 KiB default leaves a safer
reserve for the callable-service registry and ABI evolution while remaining far
below the former 3-5 KiB projection. The figures must be replaced by emitted-
binary measurements when the version-1 structures are implemented.


7. BASE PDS INVENTORY

The base PDS is expected to own:

  * descriptor, allocator and allocation-directory metadata;
  * core saved and live system settings;
  * logical-drive bindings, DPH/DPB-derived writable records, CSV/ALV policy,
    login/read-only state and other required disk session state;
  * the system search path;
  * RSX and CPX reconstruction metadata and the callable-service registry;
  * canonical date/time state and its provider binding; and
  * small shared state whose lifetime is independent of an optional module.

Command history, the live named-directory registry, security databases and
batch/flow queues are excluded from the base budget. They normally reside in
their implementing RSXs. Moving an existing mutable table into the PDS is a
ROMability and ownership change, not a RAM saving, unless its old allocation is
removed or its representation is made smaller.


8. RELEASE BOUNDARY AND CURRENT IMPLEMENTATION

The 1.0 system must have the PDS ABI, measured storage inventory, configurable
cold-boot size, stable allocations across warm boot, and the storage required
by accepted 1.0 features. Runtime expansion is an accepted architectural
capability, but need not delay 1.0 unless a required feature depends upon it.

The present Model 4 build does not yet implement the general allocator or
variable sizing. It reserves D504h through D5C3h: 192 bytes total, including
ten bytes of history control and 182 bytes of packed command records. These
addresses are current build facts, not permanent ABI values. PDS ABI 1 publishes
this static layout through the version-1 system Extension Control Block: flag
bit zero marks the view valid, its +08h word supplies the lower boundary, and
the fixed system base supplies the upper boundary. Current and configured boot
sizes are identical until configurable sizing is implemented.
